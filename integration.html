Production Integration Guide

You already run an agent, or an API, or both. This page is the wiring diagram: where payments plug into an existing production system, and the failure semantics, custody, idempotency and observability work that separates a demo from something you can leave running. Distilled from production deployments; every pattern here has paged someone.

01

Decide which half you are

Every integration is one of two jobs, and most teams eventually do both. Naming yours first keeps the scope honest.

Buyer side

Your agent pays

You run an agent (a tool loop over an LLM) and want it to buy things: paid APIs, data, other agents' services.

  • Touches: tool registry, agent loop budgets, a wallet
  • New risks: spend without consent, prompt-injected payments
  • Sections 02 to 04
Seller side

Your API charges

You run an HTTP API and want agents to pay per call, without accounts or API-key onboarding.

  • Touches: middleware or guards, a settlement wallet, ops
  • New risks: replay, facilitator outages, revenue blind spots
  • Sections 05 to 08

The protocol basics (headers, schemes, facilitators, EIP-3009) live in part one. This page assumes them.

02

Buyer: where payment plugs into the agent loop

A production agent loop usually already has two structures that payments slot straight into: a conditional tool registry and budget gates checked before every model call. Payment capability is one more gated tool plus one more budget dimension, not a rewrite.

// The registry you probably already have: capabilities gated by config
function buildToolSet(opts: ToolSetOptions): ToolSet {
  const tools = [...BASE_TOOLS];
  if (opts.paymentsEnabled) tools.push(payingFetchTool, checkBalanceTool);
  return toRegistry(tools);
}

// The budget gates you probably already have, plus one new dimension.
// All checked BEFORE the call, all abort cleanly with partial results.
while (true) {
  if (turn >= cfg.maxTurns)                 { abort("max-turns");  break; }
  if (llmCostUsd >= cfg.maxLlmCostUsd)      { abort("max-llm-usd"); break; }
  if (spendLedger.total >= cfg.maxSpendUsd) { abort("max-spend");  break; }  // new
  // ... call the model, dispatch tools, accumulate usage and spend
}

Two details make this work in practice:

Meter LLM cost and payment spend in the same place. If your loop already tracks token usage per turn into a running USD total, on-chain spend is just a second ledger next to it, checked by the same gate logic. An agent that knows "I have $0.40 of budget left" across both dimensions can decide whether a $0.05 API call is worth it.

Accumulate settlements in the run context, not the return value. Production loops abort: max turns, timeouts, LLM errors. If payment records live in a mutable context object that tools push into, an aborted run still leaves a complete audit trail of what was actually spent. A return-value design loses exactly the records you need most.

03

Buyer: rails for a paying tool

The model decides when to call the paying tool; your code decides whether the call is allowed to cost money. Treat every tool input as untrusted, because via prompt injection it is: any content the agent reads (a web page, a PR description, another agent's message) can try to steer it into paying the wrong party.

RailRuleWhy
Origin allowlistCompare parsed origins, never string prefixes. host:4021 and host:40210 share a prefix; host:4021@evil.com parses the attacker as the hostInjected URLs are the cheapest attack. The tool must be unable to pay outside the origins you configured
Price ceiling per callRead the 402 challenge, compare the amount against a configured maximum before signingA malicious seller can quote any price; the signature is what commits you
Refuse unreadable challengesA 402 whose payment header will not decode is an error, not a free passDefaulting a broken challenge to amount zero silently disables your affordability check
No dynamic recipientsThe model never supplies wallet addresses. payTo comes from the challenge; where the money can go is bounded by the origin allowlistAddress-shaped strings in model output are radioactive
Errors are results, not exceptionsReturn { ok: false, error } and surface it as an is_error tool resultThe model can react in-loop (retry, report, give up); a thrown exception kills the run and loses context
Idempotency on retriesIf your loop retries failed tools, carry an idempotency key so a flaky network cannot double-payThe expensive version of at-least-once delivery
The one-line threat model: your wallet signs whatever your code asks it to. Every rail above exists so that the path from "text the model read" to "signature produced" has a policy checkpoint your code controls.
04

Buyer: the custody ladder

Where the agent's private key lives determines your real blast radius. Climb the ladder as the money grows.

C1Env-var keyA raw private key in an environment variable. Fine for testnets and demos. Anyone with pod access owns the wallet; rotation is a redeploy.
C2Scoped hot walletStill a local key, but per agent, funded just-in-time with small amounts, refilled by policy from a treasury. Blast radius is the float, not the treasury.
C3Remote signerKMS, HSM or MPC service behind a narrow signTypedData port. The key never enters the agent process; signing requests are logged and rate-limited centrally.
C4Smart account with on-chain policyThe wallet itself enforces budgets, allowlists and per-tx caps on chain. Even a fully compromised agent cannot exceed policy. The strongest rung, and where the ecosystem is heading.

Design your signing behind an interface from day one (sign(typedData) is the whole surface EIP-3009 needs). Then climbing the ladder is a config change, not a refactor.

05

Seller: pricing is route metadata, not handler code

The cleanest production pattern: payment is declared on the route and enforced by a guard or middleware before the handler. Handlers never know they are paid. A route without the metadata is free and completely untouched, which makes rollout incremental and rollback instant.

// NestJS flavor: a decorator carrying metadata a global guard reads.
// Express/Hono flavor: the same object passed to route middleware.
@Paid({
  scheme: ["exact"],
  amount: "1000",                  // base units, decimal string, never a float
  asset: "USDC",
  network: "eip155:42161",        // CAIP-2, so chain identity is unambiguous
  discovery: {                      // machine-readable catalog metadata
    serviceName: "Example lookup",
    description: "What this endpoint returns and for whom",
    inputExample:  { /* representative values; these appear in public catalogs */ },
    outputExample: { /* ... */ },
  },
})
@Get("lookup/:id")
handler() { /* pure business logic, no payment awareness */ }

Two production refinements worth copying:

A per-environment network override. Prices and networks are baked into source, but one env var globally rewrites the chain, so staging settles on a testnet without touching any route definition.

Bypass paths as first-class config. Internal services and dashboards skip payment via an API-key allowlist; callers who bring their own upstream resources (nothing for you to monetize) skip it via a declared bypass condition. Both are explicit metadata, not special cases buried in handlers.

06

Seller: the guard pipeline, in order

Order matters: every step exists to keep a cheaper check in front of a more expensive one, and the two cache checks exist to keep you from settling the same payment twice. This sequence is the most transferable artifact on this page.

1Metadata checkNo pricing metadata on the route: free, return immediately. Zero overhead for unpaid routes.
2Internal bypassAPI-key allowlist for your own services. Compare in constant time: a Set lookup with early return leaks valid-key prefixes through response timing.
3Cost-basis bypassCaller brought their own upstream resource: nothing to monetize, wave through.
4Proof extractionFirst scheme adapter that recognizes the request's headers wins. No proof at all: emit a 402 advertising every scheme you accept, so a fresh client can pick one.
5BlocklistKnown-bad payer addresses short-circuit here, before you spend a facilitator round trip on them.
6Idempotency cacheKey by payer plus idempotency key, never the key alone, or a stranger who guesses a key replays someone else's settlement. If the payer cannot be decoded, skip the cache and re-verify: conservative beats clever.
7Verify and settleThe facilitator call, wrapped in the failure semantics of section 07, with latency and outcome metrics on every path.
8Audit writeFire-and-forget, deliberately not awaited: a degraded audit database must not stall the request path. Swallow duplicate-key errors.
9Attach receiptPut the settlement on the request object and in the response header, so handlers and clients both see what was paid.
07

Seller: failure semantics that autonomous payers can act on

Your callers are retry loops without humans in them. Whether a failure is worth retrying is the single most important bit you return, so make it explicit: every verification and settlement result carries a retriable flag, and the flag decides the status code.

What happenedretriableReturnThe agent should
Bad proof: invalid signature, expired, wrong amount, already usedfalse402 again, with the reason attached to the failing schemeSign a fresh payment or give up; retrying the same proof is pointless
Facilitator 5xx, timeout, circuit opentrue503Back off and retry the same proof; it may be perfectly valid
Verified and settled200 plus receipt headerRecord the tx hash, move on

Around the facilitator call itself, three cheap pieces of resilience pay for themselves the first bad day:

A circuit breaker. A flapping facilitator plus autonomous retry loops equals a self-inflicted flood. A simple half-open breaker (sliding failure window, cooldown, one trial call) is under a hundred lines with no dependency and turns an outage into fast, honest 503s.

A bootstrap health check. Probe the facilitator when the service starts. A misconfigured URL should fail a deploy, not the first paying customer.

Fail fast on config. If the facilitator URL implies credentials you were not given, throw at construction with a message naming the exact env vars. And normalize PEM keys read from env: secret managers and container runtimes mangle newlines, and the resulting error at request time is unreadable.

Payment bugs present as revenue anomalies, and revenue anomalies get escalated. These labels answer the questions you will actually be asked.

Plus an append-only audit row per settlement (payer, recipient, amount, asset, network, tx reference, route) and a trace span per facilitator call. On the buyer side, mirror it: one structured log line per payment with amount, tx hash and the run that spent it.

09

The hardening checklist

The gaps that separate a working integration from one you can leave alone. Each of these is invisible in a demo and expensive in production.

GapFailure mode if skippedFix
Idempotency and replay state in per-pod memoryMulti-replica deploys re-settle payments a sibling pod already saw; the on-chain nonce becomes your only backstopMove both caches to a durable shared store (Redis or a DB table with a unique constraint)
No durable spend ledgerA crash mid-run loses the record of in-flight payments; reconciliation becomes archaeologyWrite the ledger row before settling, mark it settled after; the chain is the source of truth you reconcile against
Raw keys in env vars, foreverAny pod compromise is a full wallet compromiseClimb the custody ladder (section 04); at minimum, scope and cap hot wallets
Fiat billing and per-call crypto revenue never reconciledTwo revenue systems, two dashboards, and finance questions nobody can answerLand both in one revenue table keyed by customer, whatever the rail
Payment context threaded by handPayer identity and remaining budget prop-drilled through every layer, or worse, globalPer-request context via AsyncLocalStorage, same as you already scope tenants and API keys
No queue for agent workWebhook handlers doing multi-minute paid agent runs inline, timing out with money in flightA job queue with idempotent handlers; payments make at-least-once delivery a financial property
Rate limiting only at the appThe paywall itself becomes a spend-amplification targetLimit at the gateway or CDN; keep an in-process bucket as defense in depth, with a cap on tracked keys
10

Discovery: let agents find you and behave

An agent-payable API that agents cannot discover earns nothing. Three artifacts, all cheap to serve:

Free endpoint

A pricing catalog

One unpaid route returning every paid route with scheme, amount, asset, CAIP-2 network and recipient, from the same source of truth as the guards. Agents read prices before paying.

In the 402

Catalog metadata

Ship discovery metadata (service name, description, input and output examples) on the challenge itself, so indexers and bazaars can catalog the route after their first settlement.

At the root

A capability manifest

A machine-readable page (/skill.md or similar) stating what the service does, when not to use it, the price table, and etiquette: honor Retry-After, do not re-buy cacheable data, cap payment retries.

Etiquette rules in the manifest are not decoration: autonomous callers actually follow them, and they are your first line of defense against well-meaning retry storms.
